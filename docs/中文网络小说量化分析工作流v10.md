# 中文网络小说量化分析工作流

双模型协作工作流 · 当前实现说明

---

## 一、项目概览

### 1.1 项目定位

本工作流针对中文网络小说（单部体量 50–300 万字）进行系统性量化分析，覆盖叙事结构、人物关系、情感曲线、语言风格、主题内容、传统文化传承、叙事价值立场七个核心维度，每个维度的指标均有明确的叙事学、计量文体学或语料库语言学理论来源。

### 1.2 核心架构

**「本地小模型 + 云端大模型」双模型协作体系，代码负责确定性计算，两种模型各司其职：**

| **执行者** | **职责** | **特点** |
|------------|----------|----------|
| 本地模型服务 | 高频批量任务 | OpenAI 兼容接口，承担主要标注调用量 |
| 云端模型服务 | 低频高难度任务 | OpenAI 兼容接口，负责全局推理与综合判断 |
| 代码（Python） | 所有确定性计算 | 不依赖模型，100% 准确 |

### 1.3 技术栈

| **用途** | **工具** | **说明** |
|----------|----------|----------|
| 本地推理 | OpenAI 兼容模型服务 | 用于逐块标注、增量消歧、对话归因等高频任务 |
| 结构化输出 | Pydantic + JSON Schema / JSON Object | 模型输出合同、解析与校验 |
| 中文分词 | jieba + 自定义词典 | 分词、词典指标与主题建模预处理 |
| 数据处理 | Python 聚合逻辑 + SQLAlchemy 查询 | 标注结果聚合与指标计算 |
| 人物关系图 | graph_* 权威表 + NetworkX 临时投影 | 图论指标计算；前端负责交互展示 |
| 主题建模 | gensim LDA | 主题提取与模型落盘，当前主链不默认调用云端主题命名 |
| 可视化 | React + Vite + ECharts / G6 / Force Graph | 当前交互式分析前端 |
| 持久化 | PostgreSQL + SQLAlchemy ORM | 生产级数据库，支持并发与扩展 |
| 数据库结构维护 | SQLAlchemy metadata + 启动期 schema guard + `scripts/db` | 初始化缺失表并阻断不兼容结构 |
| 云端推理 | OpenAI 兼容云端 API | 低频高难度任务与全局诊断 |
| 文本向量化 | Qwen3-Embedding / OpenAI 兼容 embedding 服务 + pgvector | 语义分块、RAG 检索与伏笔候选检索 |

## 三、工作流详解

### 3.1 阶段一：预处理

#### 理论依据

预处理阶段是整个工作流的基础，涉及文本分块、语言风格指标计算、情感词典加载等确定性操作。分块策略需保证语义完整性，避免在段落中途截断。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 原始 txt 文件 | 分块 JSON、候选人名列表、语言风格指标 |

#### 处理逻辑

**① 文本分块**

分块以 2000 字为目标，到达目标字数后等当前段落结束再切，不在段落中途截断。实际块大小因段落长短在 1800–2500 字之间浮动。

```python
def split_into_chunks(text, target=2000):
    paragraphs = text.split('\n')
    chunks, current, current_len = [], [], 0
    for para in paragraphs:
        current.append(para)
        current_len += len(para)
        if current_len >= target:
            chunks.append('\n'.join(current))
            current, current_len = [], 0
    if current:
        chunks.append('\n'.join(current))
    return chunks
```

**语义分块**：开启 `use_semantic_chunking` 时，使用 Qwen3-Embedding 兼容服务识别语义边界：
- 通过 OpenAI 兼容 embedding 服务生成段落向量
- 使用 `EmbeddingClient.compute_similarity` 计算语义相似度
- 由 `SemanticChunker` 基于语义边界进行分块
- 章节检测作为硬边界
- **配置项**：`use_semantic_chunking`、`semantic_threshold`、`semantic_max_chars`

**② 语言风格指标计算**

语言风格指标由代码直接计算，包括：
- MTLD（词汇多样性）
- TTR（型例比）
- 平均句长、句长标准差
- D值（句子离散度）
- 停顿密度（句子破碎度）
- 对话占比
- 五感词密度
- 比喻密度

**③ 情感词典加载**

加载 BosonNLP 情感词典或 NTUSD 简体版，用于后续词汇情感密度计算。

**④ jieba 分词集成**

jieba 分词用于预处理、词典指标与主题建模预处理：
- 支持自定义词典（`data/lexicons/proper_nouns.txt`）
- 配合词表统计语言风格、传统文化资源和主题语料
- 为候选实体、专有名词和网络小说高频词提供基础切分能力

### 3.2 阶段二：人名消歧（嵌入式）

#### 理论依据

从标注结果中提取人物名称，识别同一人物的不同称呼，构建全局别名表。人名消歧是人物关系分析的前提，消歧质量直接影响后续人物网络构建的准确性。

**架构说明**：人名消歧并非独立阶段，而是嵌入在标注流程中执行，采用「边标注边消解」的策略，确保早期发现的别名能及时用于后续标注。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 标注结果中提取的人物名称 | 全局别名表（alias_map） |

#### 处理逻辑

**① 两阶段消解机制**

| **阶段** | **触发时机** | **执行模型** | **目的** |
|----------|--------------|--------------|----------|
| 增量消解 | 每N块标注完成后 | 本地模型服务 | 及时识别新出现的别名，用于后续标注 |
| 最终消解 | 全部标注完成后 | 云端模型服务 | 全局一致性校验，修正增量消解的遗漏 |

**② 增强机制**

| **机制** | **说明** |
|----------|----------|
| 上下文例句注入 | 消歧时为每个候选人名提供其在原文中的上下文例句（最多3句），优先抓取包含别名提示词的句子 |
| 滚动别名表 | 标注时传入当前已知的别名表（alias_map），让模型在标注阶段就使用正式名 |
| 增量消解 | 每N块触发一次增量消解，确保早期别名及时收录并用于后续标注 |
| 已知锚点注入 | 增量消解时告知模型当前知识库中已存在的核心角色，解决"新名字无法合并到老名字"的问题 |
| 防误判说明 | 消歧 Prompt 中包含说明，防止共现句（如"伯安对贺铮说"）和说话者误识别导致的错误合并 |
| 隐性马甲识别 | 支持识别外貌描述性称呼（如"灰衣人"）与正式名字的对应关系 |
| 匿名消歧 | 全量消歧后，对匿名占位名（如`匿名_C1_0`）进行专门消歧，提供完整上下文（前一块+当前块+后一块）识别真实身份 |

**③ 别名提示词词表**

消解时优先抓取包含以下关键词的句子作为上下文例句：

| **类别** | **关键词** |
|----------|------------|
| 名字关系 | 名、字、叫、就是、称号、全名、号、绰号、别号、雅号 |
| 身份揭示 | 真容、真面目、原形、化身、伪装、真实身份、竟是、原来是 |

**④ 变体匹配机制**

解决三字及以上人名的短称匹配问题（如"贺重明"→"重明"）：

| **规则** | **说明** |
|----------|----------|
| 变体生成 | 对三字及以上人名，生成去掉首字的短称变体 |
| 变体查重 | 短称变体不与已知人名集合冲突时才使用 |
| 匹配优先级 | 全名优先匹配，变体次之 |

```python
def _get_name_variants(name: str, name_set: set[str]) -> list[str]:
    """生成候选名的字符串变体。"""
    variants = [name]
    if len(name) >= 3:
        short = name[1:]  # "贺重明" → "重明"
        if short not in name_set:
            variants.append(short)
    return variants
```

**⑤ 延迟写入与 Checkpoint 机制**

解决增量消解错误污染标注数据的问题：

| **机制** | **说明** |
|----------|----------|
| 延迟写入 | 增量消解仅更新内存中的 `memory_alias_map`，不写入数据库 |
| Checkpoint 保存 | 每隔 N 块将 `memory_alias_map` 保存到 `disambig_checkpoint` 表 |
| 最终写入 | 最终消解完成后，调用 `apply_alias_corrections` 批量修正所有标注表 |
| 断点恢复 | 任务中断后可从最近的 Checkpoint 恢复，避免重复消解 |

**数据流**：
```
增量消解 → memory_alias_map (内存)
                ↓
         Checkpoint 保存 (每N块)
                ↓
最终消解 → apply_alias_corrections → 数据库批量更新
```

**⑥ 防误合并规则**

消歧 Prompt 包含以下规则，防止错误合并：

| **规则** | **说明** |
|----------|----------|
| 共现排除 | 同一句子中同时出现的两个人名不能合并为同一人 |
| 命名句保护 | "X叫Y"、"X就是Y"等命名句中，X和Y是同一人的不同称呼 |
| 辈分排除 | 存在"爷爷/父亲/儿子"等辈分关系描述的两人名不能合并 |

**⑦ 实体类型识别与层级关系**

消歧阶段包含实体类型识别和层级关系提取：

| **实体类型** | **说明** | **示例** |
|--------------|----------|----------|
| character | 具体人物角色 | 伯安、贺重明 |
| group | 群体/队伍统称 | 赤甲卫、禁军 |
| organization | 组织/门派/家族 | 贺家、玄天道宗 |

**层级关系类型**：

| **关系类型** | **说明** | **示例** |
|--------------|----------|----------|
| belongs_to | 人物属于某组织 | 伯安 belongs_to 贺家 |
| member_of | 人物是某群体成员 | 张三 member_of 赤甲卫 |
| leader_of | 人物是某群体/组织领袖 | 贺重明 leader_of 贺家 |
| affiliated_with | 群体隶属于某组织 | 赤甲卫 affiliated_with 贺家 |

**处理规则**：
- 所有实体名称都进入消歧流程
- 消歧时识别 entity_type（character/group/organization）
- character 类型正常进行别名合并
- group/organization 类型映射到自身，不合并
- 角色、别名、关系事件最终进入 graph authority 体系（`graph_entities` / `graph_entity_aliases` / `graph_relation_events` 等）
- 层级关系不会落到旧 `entity_relations` 表族，应统一走 graph authority 投影与约束校验

**循环依赖检测**：
- 使用 DFS 算法检测关系图中的循环依赖
- 检测到循环时跳过所有涉及的关系
- 记录完整的循环路径用于调试

### 3.3 阶段三：逐块标注

#### 理论依据

本地模型对每个分块独立分析，返回结构化 JSON。标注内容涵盖情感极性、叙事结构、人物快照、人物关系变化、对话归因等维度。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 每块文本 + 别名表 + 滚动摘要 | 结构化标注数据库 |

#### 处理逻辑

**① 多阶段标注流程**

系统按 Phase1-Phase4 组织逐块标注，配置项主要控制阶段执行方式、RAG 证据注入和重试策略。

| **阶段** | **功能** | **输出字段** | **说明** |
|----------|----------|--------------|----------|
| Phase1 | 基础标注 | emotional_valence、event_type、pivot_moment、cliffhanger、characters、group_appearances、organization_appearances、location_appearances、chunk_summary | 核心叙事元素提取（不含relations） |
| Phase2 | 伏笔分析 | has_foreshadowing、setup_kind、anchor_text、setup_summary、confidence | 可结合 RAG 检索增强 |
| Phase3 | 对话归属 | dialogue_lengths、dialogue_speakers、dialogue_tones、dialogue_identity_clues | 对话长度计算、说话人归属、语气识别、身份线索提取 |
| Phase4 | 关系提取 | relations（含evidence字段） | 独立阶段，使用归一化名字，支持证据追溯 |

**执行方式**：

| **方式** | **说明** | **配置项** |
|----------|----------|------------|
| 串行执行 | Phase1 → Phase2 → Phase3 → Phase4 依次执行 | `multi_phase_annotation.parallel=false` |
| 并行执行 | Phase1/Phase2/Phase3 并行，Phase4 在消歧完成后执行 | `multi_phase_annotation.parallel=true` |

**Phase3 speaker 校验规则**：

> **核心原则：漏标注(null) > 错标注(A→B)**

Phase3 后处理（`_post_process_validation`）只做两件事：1) 校验 index 有效性；2) 别名归一化。不对 speaker 做任何丢弃或修正。

| 场景 | Prompt 规则 | 后处理行为 | 原因 |
|------|------------|-----------|------|
| LLM 不确定说话者 | 规则5：设 null | 保留 null | 漏标不错标，null 有信号可补全 |
| LLM 确定，名字在列表 | 正常输出 | 别名归一化 | 常规流程 |
| LLM 确定，名字不在列表 | 规则6：直接输出 | 保留，记日志 | 不浪费 LLM 判断，后处理无法区分"新角色"和"错判断" |

**speaker 后处理边界**：
- `identity_clue` 作为 EvidenceProfile 元数据保留，供消歧系统使用，不参与 speaker 修正
- 不从自然语言 clue 中反推 speaker，避免格式不可控导致错误修正
- speaker 归属错误（A 说的归给 B）只能靠更好的 prompt + 更多上下文改善，后处理无法弥补

**② 重试与容错机制**

四阶段标注模式下，Phase1、Phase2、Phase3、Phase4 拥有独立的重试机制：

| **阶段** | **本地重试** | **云端Fallback** | **总机会** |
|----------|--------------|------------------|------------|
| Phase1 | 3次 | 3次 | 6次 |
| Phase2 | 3次 | 3次 | 6次 |
| Phase3 | 3次 | 3次 | 6次 |

**③ 滚动摘要与上下文传递**

标注过程中维护滚动摘要，为后续块提供上下文信息。上下文机制包括：

| **机制** | **说明** | **解决的问题** |
|----------|----------|----------------|
| 全局状态注入（Global Context Padding） | 在每次 Prompt 的系统提示词中，固定写入几百字的"全局核心信息"（基础设定、核心主角名单） | 无论当前 Chunk 多短，LLM 都不会偏离大框架 |
| 滚动记忆流（Rolling Memory） | 把上一个 Chunk 的文本尾部（最后 200 字）或抽取结果摘要，作为 `<Previous_Context>` 标签拼接到当前请求中 | 解决"人祖三人继续向前走"中"三人"到底是谁的连贯性问题 |
| 动态实体注册表（Dynamic Entity Registry） | 利用 PostgreSQL 架构，在查询当前 Chunk 前，从数据库提取刚活跃过的角色状态（极简 JSON 格式），塞进当前 Prompt 的余量里 | 充当 LLM 的"短期工作记忆" |

**持久化与注入**：
- `global_context` 表存储全局核心信息
- `entity_registry` 逻辑从数据库中提取角色活跃状态快照
- `extract_global_context` 函数从前N个chunk提取核心角色和设定
- `_build_messages` 方法支持 `global_context`、`prev_tail_text`、`active_entities` 参数注入
- `run_annotate` 函数集成全局上下文提取和滚动记忆注入

**④ RAG 检索增强**

在 Phase2 伏笔分析阶段，系统使用 RAG（Retrieval-Augmented Generation）检索器增强上下文：

| **组件** | **说明** |
|----------|----------|
| EmbeddingClient | 使用 Qwen3-Embedding 模型生成文本向量 |
| RAGRetriever | 基于向量相似度检索相关上下文 |
| pgvector | PostgreSQL 向量扩展，支持高效相似度搜索 |

**RAG 检索流程**：
1. 将当前 chunk 的伏笔候选文本向量化
2. 在向量数据库中检索语义相似的历史 chunk
3. 将检索结果作为 `rag_evidence` 注入 Phase2 Prompt
4. 模型基于增强上下文判断伏笔类型和置信度

**配置项**：
- `rag.enabled`：是否启用 RAG 检索
- `rag.top_k`：检索返回的 top-k 相似 chunk
- `rag.similarity_threshold`：相似度阈值

**③ 主动排除在 Schema 之外的字段**

以下字段由代码计算，不占用模型输出：
- 句长 / 词频 / 对话占比 / 五感词 / 比喻密度 / 传统文化词密度
- 情感曲线形态 / 网络密度（关系集中度口径） / 三幕比例（代码从原始信号聚合）
- 伏笔兑现率 / 情节原型归类 / 人物弧度评分 / 叙事价值立场（全书维度，交给云端）

### 3.4 知识图谱模块

#### 理论依据

知识图谱是角色信息的权威来源，用于支持标注阶段的上下文增强、聚合阶段的图论计算、诊断阶段的图谱摘要、报告阶段的网络可视化。

#### 三层定义

| **层级** | **载体** | **角色** | **生命周期** |
|----------|----------|----------|--------------|
| 根证据层 | chunk_* 表 | 保留逐块事实和原始证据 | 永久存储 |
| 权威语义层 | graph_* 表 | 统一角色、别名、关系的结构化真值 | 永久存储 |
| 计算层 | NetworkX | 临时构建，用于图论计算 | 用完即弃 |

**核心原则**：
- NetworkX 不是持久化方案，只是计算时的临时投影
- 图谱表是权威语义层，所有查询都从这里读取
- 根证据层提供可追溯的证据来源

#### 图谱表设计

| **表名** | **用途** | **核心字段** |
|----------|----------|--------------|
| graph_entities | 实体权威表 | canonical_name, entity_type, first_seen_chunk, last_seen_chunk, status |
| graph_entity_aliases | 别名表 | entity_id, alias, source_chunk_id, confidence |
| graph_relation_events | 关系事件历史 | from_entity_id, to_entity_id, relation_type, change_type, chunk_id, evidence |
| graph_relations_current | 当前关系快照 | from_entity_id, to_entity_id, current_type, change_count, tension_index, is_active |
| graph_entity_participants | 图谱参与度快照 | entity_id, relation_event_count, current_degree, historical_degree |

#### 图谱投影机制

**投影时机**：
- 标注过程中按区间增量投影，避免整书结束前图谱长期空白
- 最终消歧完成后执行一次 `rebuild=True` 全量重建，确保别名归一化与图谱快照一致

**投影流程**：
```
Phase1 → Phase2/Phase3（并行）
    ↓
Phase4（关系提取）
    ↓
按 projection_interval 增量 project_graph_tables()
    ↓
最终消歧完成
    ↓
project_graph_tables(rebuild=True)
    ↓
graph_entities / graph_relation_events / graph_relations_current 写入
```

**NetworkX 使用边界**：
- ✅ 允许：图论指标计算（中心性、聚类系数、最短路径）
- ✅ 允许：可视化前的临时构建
- ❌ 禁止：作为持久化存储
- ❌ 禁止：跨 chunk 累积状态

#### 与各阶段的集成

| **阶段** | **图谱参与方式** | **查询内容** |
|----------|------------------|--------------|
| 标注阶段 | RAG Level2 增强 | 活跃角色列表、关系上下文 |
| 聚合阶段 | 图结构聚合 | 中心性、聚类系数、网络密度（字段兼容名，现按关系集中度计算） |
| 诊断阶段 | 图谱摘要 | 核心关系链、关键转折点 |
| 报告阶段 | 网络可视化 | 关系网络图、角色影响力 |

#### 断点恢复机制

当标注过程中断时，当前恢复依赖：
1. `analysis_runs` 中的任务状态与阶段完成情况
2. `disambig_checkpoint` 中的别名 checkpoint
3. 图谱读取面的 readiness gate；未完成投影不会静默返回旧快照

### 3.5 阶段五：指标聚合

#### 理论依据

代码从本地模型输出的原始信号字段聚合得出最终指标。核心原则：代码能算的绝不交给模型，模型只输出「原始信号字段」。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 标注数据库 | 七维聚合指标 |

#### 处理逻辑

**① 指标来源分层**

| **来源** | **执行方式** | **可靠性** | **典型指标** |
|----------|--------------|------------|--------------|
| 来源一：代码直接计算 | 预处理阶段并行运行，无需模型 | 100%（确定性算法） | MTLD、句长、TTR、对话占比、D值、停顿密度 |
| 来源二：模型输出原始信号，代码聚合 | 模型输出逐块字段，事后图结构聚合 | 中（依赖模型信号质量） | 情感曲线形态、高潮间距、网络密度（关系集中度口径） |
| 来源三：必须由模型直接输出 | 语义理解不可或缺，代码无法替代 | 低–中 | emotional_valence、pivot_moment、event_type、伏笔标记、人物关系、叙事价值立场 |

**② A/B 两类指标分开报告**

| **类型** | **维度** | **测量方法** | **报告方式** | **可跨书比较** |
|----------|----------|--------------|--------------|----------------|
| A 类：可量化指标 | 语言风格（全部） | 代码直接计算 | 数值，可排序 | ✅ 可以 |
| A 类：可量化指标 | 叙事结构（表面） | 代码：章节长度方差、对话占比分布 | 数值 | ✅ 可以 |
| B 类：解释性判断 | 情感弧度、人物深度 | 云端模型采样分析 | 自然语言，不出分值 | ❌ 不跨书比较 |
| B 类：解释性判断 | 主题内容 | LDA + 云端命名 | 主题列表 + 说明 | ⚠️ 相对比较 |

### 3.6 阶段六：主题建模

#### 理论依据

**LDA 隐狄利克雷分配（Blei et al. 2003）**：无监督概率生成模型，基于词袋假设，认为每篇文档是多个隐藏主题的混合，每个主题是词语的概率分布。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 全书分词语料 | 主题分布 + 主题模型文件 |

#### 处理逻辑

**① LDA 参数设置**

| **参数** | **单书分析** | **多书横向比较** | **说明** |
|----------|--------------|------------------|----------|
| 主题数 K | 20–30 | 100–150 | 单书主题太多会产生高度相似的冗余主题 |
| 文档单元 | 每块（~2000字） | 每章 | 按章节切分更符合叙事单元 |
| 每主题输出词数 | 前 15 词 | 前 20 词 | |
| 迭代次数 | 500 | 1000 | 多书语料更大，需更多迭代 |

**② 主题标签说明**

当前主链只保证：
- 本地 LDA 训练
- `chunk_topics` 落库
- 主题模型文件保存到磁盘

如果模型文件内已经带有 `labels`，结果接口会优先读取；**云端主题命名目前不属于默认主链合同**，若恢复应作为独立增强重新设计。

### 3.7 阶段七：深度分析

#### 理论依据

深度分析阶段由云端模型承担，负责需要全局推理与综合判断的高难度任务。云端模型在结构事件和原始文本上做推理，不在聚合数值上做推理。

#### 输入输出

| **输入** | **输出** |
|----------|----------|
| 全书摘要 + 指标汇总 | 伏笔验证 / 人物弧度 / 宏观诊断 / 叙事价值立场 |

#### 处理逻辑

**① 伏笔兑现验证**

本地模型只能标记「此处有伏笔」，无法判断后续是否兑现。云端模型在全书标注完成后，接收伏笔摘要列表，在全书结构摘要中检索对应回收场景，输出兑现率评分。

**② 人物弧度综合评估**

接收主要人物的全书行为/情感序列摘要，评估弧度完整性，判断性格转变是否有充分铺垫，输出自然语言评估报告。人物弧度是解释性判断，不以数值评分为结论。

**③ 宏观结构诊断**

云端模型当前主链输入由以下结构化信息构成：

```python
cloud_input = {
    'pivot_blocks': get_top_k_by_semantic_shift(chunk_vecs, k=10),
    'pivot_moments': get_pivot_moment_summaries(annotations),
    'high_tension_paragraphs': get_high_tension_chunks(chunk_style, top_pct=0.1),
    'character_relations': get_relation_changes(chunk_relations),
    'foreshadow_expectation': build_foreshadow_expectation(chunk_foreshadowing),
    'foreshadowing_threads': fetch_foreshadowing_threads(),
    'summaries': fetch_stage_summaries(),
    'topic_words': fetch_topic_words(),
    'known_characters': fetch_character_disambig_data()[0],
    'alias_merges': fetch_character_disambig_data()[1],
    'graph_summary': build_graph_summary(),
    'graph_quality_report': build_graph_quality_report(),
}
```

**核心原则：** 云端模型在结构事件和原始文本上做推理，不在聚合数值上做推理。输出是解释性判断（自然语言），不是对数字的再统计。

**④ 叙事价值立场评估**

在宏观结构诊断的同一次调用中，追加以下三个判断问题，不单独开启调用：

| **判断维度** | **具体问题** | **评分标准** |
|--------------|--------------|--------------|
| 强欺弱场景的叙事倾向 | 书中强者欺压弱者场景，叙事情感倾向是谴责、中立还是欣赏？ | 0=欣赏强者 2=中立 5=谴责压迫 |
| 普通人的叙事尊严 | 普通配角受难时是被认真书写还是仅作背景板？ | 0=纯背景板 2=偶有描写 5=认真书写 |
| 核心价值逻辑 | 全书最终传递的核心价值逻辑是善义有价值、强者为王还是混合型？ | 文字说明 + 代表性依据段落 |

**设计说明：** 叙事价值立场是对叙事道德判断方向的测量，与传统文化维度不重叠。传统文化维度测量的是「用了什么文化资源」，叙事价值立场测量的是「站在谁那边」，两者可以独立变化。

## 四、维度与指标

> **详细指标说明请参阅：《中文网络小说指标参考手册.md》**
>
> 该手册包含 52 个指标的完整说明，涵盖：
> - 字段名、取值范围、高低含义
> - 数据来源、计算方法
> - 理论来源与学术依据
> - A类/B类指标分类

### 4.1 七大分析维度概览

| **维度** | **核心内容** | **主要指标类型** |
|----------|--------------|------------------|
| 维度一：叙事结构 | 故事骨架的完整性、节奏分布与悬念设计 | 三幕比例、事件密度、高潮间距、悬念保持率、伏笔兑现率 |
| 维度二：情感曲线 | 四条独立曲线（词汇情感密度、节奏代理、情感极性、语义跳跃） | 曲线形态、正负词汇比、节奏波动幅度、情感恢复速度 |
| 维度三：人物关系 | 社会网络分析量化人物结构地位 | 人物度中心性、网络密度（关系集中度口径）、人物功能覆盖率、弧度完整性 |
| 维度四：语言风格 | 全部由代码确定性计算，100% 可重复验证 | MTLD、TTR、句长、D值、五感词密度、比喻密度 |
| 维度五：主题内容 | LDA 主题建模 + diagnosis 主题标签 | 主题分布、主题语义命名 |
| 维度六：传统文化传承 | 测量文本使用的传统文化资源 | 儒道佛民间典故词密度、四字成语密度、古典句式比例 |
| 维度七：叙事价值立场 | 测量叙事者「站在谁那边」 | 强欺弱叙事倾向、普通人叙事尊严、核心价值逻辑 |

### 4.2 情感曲线平滑方法

当前 `smoothed_density` 使用傅里叶变换频域滤波平滑（参考 Matthew Jockers《畅销书写作密码》）：

| **步骤** | **说明** |
|----------|----------|
| 离散傅里叶变换 | 对情感密度数组做 DFT，转换到频域 |
| 保留低频分量 | 保留宏观故事弧（低频），过滤逐句波动（高频噪声） |
| 逆变换 | 做逆变换得到贴近真实叙事节奏的平滑曲线 |

### 4.3 人物情绪字段口径

当前 `emotion_score` 与 `emotional_valence` 使用同一套五档枚举，聚合与前端展示时再映射为数值：

| **枚举** | **聚合映射** |
|----------|--------------|
| strong_positive | 2 |
| mild_positive | 1 |
| neutral | 0 |
| mild_negative | -1 |
| strong_negative | -2 |

### 4.4 关系张力指数

关系事件先进入 `chunk_relations` 和 `graph_relation_events`，当前关系快照由 `graph_relations_current` 承载，其中 `tension_index` 用于描述关系当前张力：

- **量化场景**：盟友关系但也可能张力极高（各怀鬼胎）
- **存储方案**：持久化在 `graph_relations_current.tension_index`，计算时可临时构建 NetworkX 图

### 4.5 指标类型说明

| 类型 | 含义 | 可跨书比较 | 典型来源 |
|------|------|-----------|---------|
| **A类** | 结果确定，可重复验证，误差来源明确 | ✅ 可以，可做统计比较 | 代码计算、代码聚合 |
| **A类有限** | 依赖模型信号，稳定性较高但非100%确定 | ⚠️ 有限比较 | 本地模型聚合 |
| **B类** | 叙事质量是解释性概念，不追求精确分值 | ❌ 不出精确分值 | 云端模型综合判断 |

| 叙事价值立场 | 合并入宏观诊断云端调用 | 无需词表，只需修改 prompt 文件 |

### 5.2 词表建设原则

1. **覆盖高频核心词即可**：各类词表词条数建议 50–150 条，追求召回率而非完美覆盖
2. **词表只做粗筛**：定量工作由词表完成，真实性校验交给云端模型（定性）
3. **贴近网络小说实际语言**：儒道佛三类词表不应直接照搬学术辞典，需收录网络小说实际使用频率高的通俗化用词
4. **典故词表可复用现有资源**：可参考现有典故词典（如《汉语成语词典》《中华典故大全》）导入后筛选，无需从零建设

### 5.3 词表启用口径

| **类别** | **启用方式** | **影响维度** |
|----------|--------------|--------------|
| 高优先级词表 | 基础工作流可直接加载 | 情感曲线、语言风格、人物候选、异常检测 |
| 传统文化词表 | 词表存在时参与粗筛统计 | 传统文化传承 |
| 无需词表指标 | 正则或代码直接计算 | 对话占比、比喻密度、古典句式比例、叙事价值立场 |

## 七、双模型分工设计

### 7.1 分工原则

| **维度** | **本地小模型** | **云端大模型** |
|----------|------------------------------|------------------------------|
| 调用频次 | 高频（每块一次，数百次） | 低频（每部书 5–15 次） |
| 任务难度 | 结构化提取、局部语义理解 | 跨章节推理、综合判断 |
| 上下文长度 | 单块 ~2000 字 + 滚动摘要 | 全书摘要 + 关键片段 |
| 成本 | 零（本地 GPU） | 按 token 计费，单书 < $2 |
| 输出格式 | 严格 JSON（Pydantic 校验） | 自然语言报告 / JSON 均可 |

### 7.2 本地模型职责（高频任务）

| **任务** | **说明** |
|----------|----------|
| 逐块情感与事件标注 | 对每个分块独立分析，返回结构化 JSON |
| 人名消解（增量） | 每N块触发一次，识别新出现的别名，及时用于后续标注 |
| 对话归因 | 识别每段对话的说话人及语气类型 |

### 7.3 云端模型职责（低频高难度任务）

| **任务** | **说明** |
|----------|----------|
| 人名消解（最终） | 全部标注完成后进行全局一致性校验，修正增量消解的遗漏 |
| 伏笔兑现验证 | 接收伏笔摘要列表，检索对应回收场景，输出兑现率评分 |
| 人物弧度综合评估 | 评估弧度完整性，判断性格转变是否有充分铺垫 |
| 宏观结构诊断 | 在结构事件和原始文本上做推理，输出解释性判断 |
| LDA 主题命名（可选增强） | 当前主链不默认执行；若恢复需作为独立增强重新设计 |
| 多书横向比较报告 | 生成跨书对比分析报告 |
| 叙事价值立场评估 | 判断叙事道德立场（合并入宏观诊断） |

## 八、模型质量保障

### 8.1 噪声来源

| **噪声类型** | **具体表现** | **影响程度** |
|--------------|--------------|--------------|
| 一致性噪声 | 同一段文字不同批次运行可能得到不同分类结果 | 中 |
| 边界噪声 | emotional_valence 在正负边界的段落上分类不稳定 | 中 |
| 语境噪声 | 「她笑着走向死亡」被表面词义误导 | 高 |

### 8.2 控制手段

| **手段** | **说明** |
|----------|----------|
| 相对排序替代绝对分值 | 情感曲线分析只需要相对判断，滑动平均平滑单点噪声 |
| 云端模型抽样校验 | 每 50 块随机抽 5 块同时送云端做三分类，计算一致率 |
| 规则层兜底异常检测 | 若 emotional_valence=neutral 但战斗词密度极高，触发云端复核 |
| 关键块多次采样取中位数 | 对高张力区域的关键块做 3 次独立推理取中位数 |
| 锚点示例注入 Prompt | 在 prompt 中提供具体参考样例，覆盖边界情况 |

### 8.3 各指标可信度评级

| **指标** | **可信度** | **来源** |

| 语言风格全部指标 | ★★★★★ | 代码 |
| 节奏代理信号 | ★★★★ | 代码 |

| 事件类型分类 | ★★★ | 本地模型 |

### 9.2 理论本土化

上述来自西方的理论直接套用中文网络小说存在系统性偏差，需要本土化处理：

| **偏差类型** | **具体表现** | **本土化处理** |
|--------------|--------------|----------------|
| 情感曲线模式不同 | 网络小说受「爽文」机制驱动，典型曲线是高频小正峰叠加、整体持续上升 | 将「高潮密度」而非「高潮高度」作为主要衡量维度 |
| 伏笔逻辑不同 | 中国古典叙事「草蛇灰线」更强调意象呼应，不要求严格逻辑兑现 | 将伏笔分为 causal（因果型）和 thematic（意象型）两类分别验证 |
| 人物功能密度更高 | 网络小说一章内可能出现多次功能切换 | 改用「功能覆盖率 × 章节数」归一化 |
| 传统文化词表本土化 | 儒道佛三类词表不应直接照搬学术辞典 | 收录网络小说实际使用频率高的通俗化用词 |
| 叙事价值立场参照系 | 网络小说整体偏向强者逻辑 | 「中立」基准应基于类型内部比较 |

## 十、已知局限

| **问题** | **影响维度** | **处理建议** |
|-----------|--------------|--------------|
| 极低频路人角色识别缺失 | 人物关系 | 接受损失，主要人物覆盖率 > 95% |
| 纯代词指代难以消歧 | 情感归因 | 标记为「未知视角」，不纳入人物弧度计算 |
| 跨 50 章以上的超长伏笔 | 伏笔兑现率 | 云端分析时注入更多章节摘要 |
| 仙侠/修仙功法体系词汇分词错误 | 语言风格 | 预置专有词表覆盖高频奇葩词 |
| TTR 受长度影响 | 词汇多样性 | 跨书比较时须等长切分，单书用 MTLD |
| 情感绝对分值不可精确比较 | 情感曲线 | 以趋势和排序为主，不直接报告精确数值 |
| 理论指标均来自西方语料基准 | 所有维度 | 只做同类型小说横向比较，不与西方基准对齐 |
| 传统文化词表覆盖不完整 | 传统文化 | 词表只做粗筛，云端校验文化内涵真实性 |
| 叙事价值立场判断主观性较高 | 叙事价值立场 | 多书比较时看排序趋势，不报告精确分值差异 |
