## 二、根问题分层

### 2.1 判决机制层（核心）

- 一次性判决偏重，证据积累不足
- 早期误判难以被后续新证据自动纠正
- 对"自动合并"缺少强制证据门槛

### 2.2 候选质量层

- 候选中混入大量"默认不应自动合并"的名称类型
- 缺少统一负类策略，导致下游模型负担过重

### 2.3 可验证性层

- 缺少固定评测口径和基线报表
- 改动后只能"主观感觉变好/变坏"，无法稳定证明收益

### 2.4 可审计性层

- 难以回答"这次合并凭什么成立"
- 缺乏决策证据、评分构成、回滚触发的结构化记录

## 三、已尝试/已讨论方案复盘（为什么不行）

> 说明：这里按"是否能稳定提升准确率"评估，而不是按"是否能减少报错"评估。

### 3.1 小修补类方案（已做/多次做）

典型内容：

- 修补某个触发条件
- 修复单一函数中的逻辑偏差
- 调整少量 prompt 文案

短期收益：

- 能修掉已知单点 bug
- 能避免少数明显错误路径

为什么不行：

- 不改变"一次性判决 + 弱约束"的主结构
- 无法形成可持续的准确率增益
- 新样本上容易出现同类问题

结论：必要但不充分，只能当保底修复，不是重构主线。

### 3.2 方案 A（延迟决策 + 证据积累）

核心思路：

- 先积累证据，再决策
- 引入候选队列和分数阈值

价值：

- 方向正确，能抑制"过早合并"

为什么单独落地不够：

- 若没有统一评测与审计，分数阈值容易拍脑袋
- 若没有复审状态机，仍会出现"低质量自动通过"
- 若没有硬约束输出协议，LLM 仍可能给出缺证据结论

结论：可作为子模块，不应单独作为全局重构方案。

### 3.3 方案 C（置信度生命周期 + 约束传播）

核心思路：

- 状态机 + 可降级 + 矛盾检测

价值：

- 理论完整，支持回滚与修正

为什么直接上风险高：

- 实现复杂，规则边界多，若无基线系统会"复杂但不可证优"
- 容易陷入工程投入大、效果证明弱

结论：应分阶段做 C-lite，再做 C-full，不宜一步到位。

### 3.4 方案 B/E/F（候选过滤、规则优先、数据闭环）

共同问题：

- 单独实施时，只能优化某一环，无法闭环
- 没有统一门禁时，提升不可持续

结论：可作为增强件，不能替代主架构重构。

### 3.5 方案 D（双模型裁决，后置增强）

适用前提：

- 候选质量问题已被明显压降（泛指/群体/外貌描述误入消歧显著减少）
- 基线系统已稳定运行，能够量化"判决质量问题"而非"候选质量问题"

优势：

- 可抑制单模型在边界样本上的一次性误判
- 对高风险自动合并提供二次保险

限制：

- 成本和时延直接翻倍
- 若主问题仍是候选质量，收益很低

结论：不作为当前主干，放在 P2/P3 条件触发。

## 四、重构主方案（本轮推荐）

## 4.1 总体策略

以"基线先行 + 候选治理"为主干，组合三项基础能力：

1. 评测基线系统（先有量尺）  
2. 候选质量治理（先降主要错误源）  
3. 复审与审计（可纠错、可追溯）

即：`Baseline + CandidateQuality + Review + Audit`

### 4.2 架构目标

- 目标 1：自动合并必须证据充分且可审计
- 目标 2：低置信决策可延后、可复审、可回滚
- 目标 3：每次迭代都能和初版做同口径对比
- 目标 4：优先解决"不该进入消歧的候选"问题

### 4.3 分阶段落地

#### 阶段 P0：基线系统先落地

- 固定 run 集与指标口径（冻结 task_id 清单）
- 至少完成 1 轮完整采集：自动报表 + 人工标注对照
- 形成首版"误合并/正确合并/review"金标样本集

#### 阶段 P1：候选质量治理

- 泛指名、群体名、外貌描述名分流（默认不自动合并）
- 例句池增加命名关键词优先级
- 将"候选误入消歧率"纳入主监控指标

#### 阶段 P1.5：复审队列

- review 名字进入待复审池
- 后续新增证据触发重新评估
- 对已确认但发生冲突的决策支持降级

#### 阶段 P2：判决增强按条件触发

- 当候选质量问题已压降后，再评估双模型裁决
- 训练数据闭环（hard negative 集）按收益推进

### 4.4 证据门禁（可执行定义）

"无证据不得自动高置信合并"不依赖自然语言 reasoning，而依赖结构化字段校验。

建议新增并校验字段：

- `decision_evidence_count`: 该次 merge 命中的证据条数（整数）
- `decision_evidence_types`: 证据类型数组（如 naming_sentence/co_occurrence）
- `decision_evidence_chunks`: 证据所在 chunk_id 列表

门禁规则：

- 自动高置信 merge 必须满足 `decision_evidence_count >= 1`
- 且 `decision_evidence_types` 非空
- 否则强制降级为 `review`

---

## 五、验收标准（必须量化）

与"当前初版 Baseline"对比，至少满足：

1. 误合并率显著下降  
2. 自动合并准确率上升或持平  
3. 候选误入消歧率显著下降  
4. 可复审样本中，后证据纠错成功率可观  
5. 自动高置信 merge 的结构化证据字段覆盖率达标（100% 可校验）

若未满足以上条件，不判定为"重构成功"。

## 六、不再采用的推进方式

1. 继续以小修补替代结构改造  
2. 仅调 prompt、不改判决协议与门禁  
3. 无基线报表就宣称"准确率提升"  
4. 先做高复杂状态机，再补评测与审计

## 十、P0 基线审查发现 — 实体类型识别链路断裂

### 10.1 金标审查发现的典型误合并

对 `6b401f00`（重明传）8 条记录的人工标注暴露了两类系统性 bug：

| # | alias | canonical | 系统判断 | 人工判断 | 错误类型 |
|---|-------|-----------|---------|---------|---------|
| 2 | 灵禽 | 赤羽炽尾鸡 | should_merge | **should_not_merge** | 物种→个体误合并 |
| 7 | 赵哥 | 赤甲卫 | should_merge | **should_not_merge** | 个人→组织误合并 |
| 5 | 柳婉儿 | 柳妹妹 | should_merge | should_merge | 规范名方向反（次要问题） |

**核心问题**：LLM 始终不识别 organization/animal 等非 character 类型。

### 10.2 根因分析 — 四层断裂

#### 层面 1：Prompt 缺少实体类型词汇

`config/prompts/disambiguate.txt` 的实体类型规则只提供了 3 种：

```
【实体类型识别规则】
- character：具体人物角色
- group：群体/队伍统称
- organization：组织/门派/家族
```

**没有 animal/creature/species/artifact 等类型**。玄幻小说常见的灵兽、法宝等实体类型完全缺失。LLM 只能在三选一，自然全部归到 character。

#### 层面 2：Schema 无枚举约束

`src/models/local/schema.py:303-306` 的 `entity_types` 字段是 `dict[str, str]`（free text），而非 `Literal[...]`。Instructor 不会做枚举校验，但 LLM 也不会输出 prompt 未教的类型。

#### 层面 3：下游代码全面 fallback 到 "character"

| 文件:行号 | 问题 |
|----------|------|
| `graph_projection.py:148,189,244,252` | 4 处硬编码 `entity_type="character"`，完全忽略消歧结果中的 entity_types |
| `characters.py:118` | `entity_types.get(canonical, "character")` — 找不到就默认 character |
| `relations.py:293,299` | 同上 fallback 到 character |

#### 层面 4：`valid_entity_types` 配置是死代码

`src/config/schemas/annotation.py:89-90` 定义了 `["character", "group", "organization"]`，但：
- 没有任何代码在构建 prompt 时读取此配置
- 没有任何代码在接收 LLM 输出后校验 entity_type value 是否合法

### 10.3 修复影响范围

修复需要同步改动以下位置：

| 优先级 | 文件 | 改动 |
|--------|------|------|
| P1 | `config/prompts/disambiguate.txt` | prompt 增加 species/creature/artifact 类型说明 |
| P1 | `src/models/local/schema.py:303` | `entity_types` value 改为 Literal 枚举 |
| P1 | `src/config/schemas/annotation.py:90` | `valid_entity_types` 扩展并实际消费 |
| P1 | `src/models/local/disambiguation/messages.py` | `_build_dynamic_system_prompt()` 注入实体类型 |
| P1 | `src/workflows/annotate_helpers/graph_projection.py` | 去除 4 处硬编码 `entity_type="character"` |
| P1 | `src/storage/repositories/annotation/characters.py:118` | fallback 逻辑需考虑新类型 |

### 10.3.1 P1.1 补充：entity_types 传递链路断裂（实施中发现）

P1.1 原始修复解决了 prompt/schema/graph_projection 三层，但实施验证时发现第四层断裂：

**问题**：LLM 在增量消歧早期正确输出 `赤甲卫=group`，但 `DisambiguationState` 不持久化 entity_types，`ensure_canonical_entities` 在终消歧时只能拿到最后一次 LLM 调用的 entity_types，导致赤甲卫在 graph_entities 中仍被标记为 character。

**修复**：

| 文件 | 改动 |
|------|------|
| `src/models/local/disambiguation/state.py` | `DisambiguationState` 增加 `entity_types: dict[str, str]` 字段，to_dict/from_dict 持久化 |
| `src/workflows/annotate_helpers/disambiguation/pipeline.py` | 增量消歧累积 LLM 输出的 entity_types 到 state；终消歧使用累积的 entity_types 传给 ensure_canonical_entities |

### 10.4 与金标评测的关联

- 误合并率中的"物种→个体"和"个人→组织"两类错误，直接源于实体类型链路断裂
- 修复后这两类误合并应降至 0
- 可作为 P1 验收指标：`eval_disambig_baseline.py` 中新增"按实体类型分组的误合并率"

## 十二、P0 发现的三个系统性 Bug

### Bug #1：实体类型识别链路断裂（详见 §10）

- **影响**：3/5 误合并（灵禽→赤羽炽尾鸡、赵哥→赤甲卫、赤甲卫→伯安）
- **根因**：prompt 只有 3 种类型 + graph_projection 硬编码 character + schema 无枚举约束 + valid_entity_types 死代码
- **修复范围**：6 个文件（见 §10.3）

### Bug #2：canonical 方向不稳定

- **影响**：4/4 漏合并（柳婉儿↔柳妹妹、柱子↔褚大山、猴子↔侯飞白、算盘↔林立果）
- **表现**：系统有时选高频名作 canonical，有时选低频名，无统一规则
- **原文频次验证**：

| alias（低频） | canonical（高频） | 比例 | 系统选择 |
|--------------|-----------------|------|---------|
| 褚大山 (3) | 柱子 (34) | 11:1 | ❌ 褚大山 |
| 柳妹妹 (2) | 柳婉儿 (9) | 4.5:1 | ✅ 柳婉儿 |
| 林立果 (7) | 算盘 (45) | 6.4:1 | ❌ 林立果 |
| 侯飞白 (6) | 猴子 (57) | 9.5:1 | ❌ 侯飞白 |
| 凤兰 (17) | 周凤兰 (13) | 1.3:1 | ❌ 周凤兰 |

- **原判根因**：候选选择逻辑中 canonical 确定规则不统一，可能在 `candidates.py`、`state.py` 或消歧 prompt 中有多种来源相互矛盾
- **实际根因（P1.2 实施中修正）**：
  1. **增量消歧 LLM 未识别别名对**：猴子/侯飞白等名字在不同 chunk 被独立发现，增量消歧中 LLM 缺少已有角色的上下文例句（`rag_hint`），导致多数调用中 LLM 输出 self-map（name→name），根本没做出合并决策
  2. **`align_canonical_by_frequency` 前提不满足**：该函数只能翻转已有的 (alias→canonical) 方向，不能为 LLM 未识别的别名对创建新合并
  3. **增量消歧设计遗漏**：`pipeline.py` 增量消歧调用 `_retry_disambig` 时未传 `rag_hint`（已有角色上下文提示），而终消歧传了；导致增量阶段 LLM 只看到名字列表，看不到已有角色的例句
- **修复方向**：
  1. 增量消歧补传 `rag_hint`（`pipeline.py`），让 LLM 能看到已有角色的上下文
  2. 保留 `align_canonical_by_frequency` 作为频次方向修正的后置保障

### Bug #3：跨 run 一致性缺失

- **影响**：1/5 误合并（白芷→贺铮）
- **表现**：6b401f00 中灰衣人→白芷（should_merge，白芷独立存在），abededd4 中白芷→贺铮（should_not_merge）
- **根因**：消歧状态是 per-run 隔离的，同一小说的不同 run 无法共享已确认的实体映射。当 run A 确认了"白芷是独立角色"，run B 不会继承这一结论
- **修复方向**：P1 暂不修复（需要 novel_id 级别的跨 run 状态共享机制，复杂度较高），在金标中标记为已知问题，P2 再评估

## 十六、步骤 3 方案：图谱反哺消歧（设计阶段）

### 16.1 当前 rag_hint 的数据链路

消歧阶段的 `rag_hint` 由 `_build_existing_character_hint_from_db()` 构建（`candidates.py` L167-179）：

```
chunk_characters + chunk_dialogues → build_context_sentences() → build_existing_character_hint()
```

**完全从 chunk 表构建，不读任何 graph_* 表。**

同时，annotate 阶段已有独立的 `DisambigContextProvider`（`src/rag/retriever.py`），它**确实读图谱**（`fetch_alias_map`、`fetch_active_entities`），但仅服务于标注阶段的 prompt 注入（`known_aliases_str`），与消歧阶段的 rag_hint 完全独立。

### 16.2 核心差距

| 设计要求 | 实际状态 |
|----------|----------|
| disambig 阶段从图谱读候选映射 | **完全未实现** — rag_hint 不查图谱 |
| disambig 阶段利用图谱关系上下文 | **完全未实现** |
| 图谱增强应该是"补充"而非"替代" | 当前无增强 |

两套独立的上下文管道：
- annotate 阶段：`DisambigContextProvider`（读图谱别名 + 活跃实体）
- disambig 阶段：`_build_existing_character_hint_from_db`（只读 chunk 表）

### 16.3 方案设计：图谱增强 rag_hint

**目标**：在消歧 rag_hint 中注入图谱已裁决的权威别名和关系信息，帮助 LLM 做更准确的消歧决策。

**改造点**：`candidates.py` 的 `_build_existing_character_hint_from_db`

**增强维度**：

| 维度 | 图谱数据源 | 增强效果 |
|------|-----------|----------|
| 权威别名 | `fetch_alias_map()` | 注入"X 是 Y 的别名（图谱已裁决）" |
| 角色类型 | `fetch_entities()` | 在锚点中补充 entity_type |
| 已知关系 | `fetch_current_relations()` | 注入"X 与 Y 是师徒/敌对关系" |

**新增函数**：`_augment_hint_with_graph(hint, graph_repo, run_id, existing_names)`

```python
def _augment_hint_with_graph(
    hint: str,
    graph_repo: GraphRepository,
    run_id: str,
    existing_names: list[str],
) -> str:
    """在 rag_hint 末尾追加图谱权威信息。"""
    lines = [hint or ""]

    # 1. 权威别名
    alias_map = graph_repo.fetch_alias_map(run_id)
    graph_aliases = {a: c for a, c in alias_map.items() if a != c and c in existing_names}
    if graph_aliases:
        alias_lines = ["【图谱已裁决的别名映射】"]
        for alias, canonical in sorted(graph_aliases.items()):
            alias_lines.append(f"- {alias} → {canonical}")
        lines.append("\n".join(alias_lines))

    # 2. 当前生效关系
    relations = graph_repo.fetch_current_relations(run_id, active_only=True)
    relevant_rels = [
        r for r in relations
        if r["from_name"] in existing_names or r["to_name"] in existing_names
    ]
    if relevant_rels:
        rel_lines = ["【图谱已确认的关系】"]
        for r in relevant_rels[:10]:
            rel_lines.append(f"- {r['from_name']} ←{r['type']}→ {r['to_name']}")
        lines.append("\n".join(rel_lines))

    return "\n".join(lines)
```

**调用侧改造**：`pipeline.py` 中两次调用 `_build_existing_character_hint_from_db` 的地方传入 `graph_repo`：

```python
# 增量消歧（L310）
rag_hint = _build_existing_character_hint_from_db(
    conn, new_names, existing_names, alias_keywords, run_id,
    graph_repo=graph_repo,
)

# 终消歧（L428）
rag_hint = _build_existing_character_hint_from_db(
    conn, all_names, existing_names, alias_keywords, run_id,
    graph_repo=graph_repo,
)
```

### 16.4 降级机制

当 `graph_repo` 为 None 或图谱数据为空时，回退到当前的纯 chunk 表逻辑。这保证：
- 图谱不可用时消歧仍然正常工作
- 早期 chunks（图谱尚未投影）不受影响

### 16.5 风险与约束

| 风险 | 缓解 |
|------|------|
| 图谱错误放大 | 前置条件已满足（步骤 1+2），当前 0 错误 |
| prompt 过长 | 限制关系条数（top 10），别名截断 |
| 早期 chunks 无图谱数据 | graph_repo=None 时跳过增强 |

### 16.6 预期效果

1. **别名裁决一致性**：图谱已裁决的别名（如 猴子→侯飞白）会直接告诉 LLM，避免重复推理或矛盾决策
2. **关系辅助消歧**：如果 LLM 知道"伯安 belongs_to 贺家"和"贺铮 leader_of 贺家"，就不太可能把伯安和贺铮合并
3. **跨 chunk 信息传递**：当前 rag_hint 只能看到 chunk 表中的原文证据，图谱提供了跨 chunk 聚合后的高阶语义
